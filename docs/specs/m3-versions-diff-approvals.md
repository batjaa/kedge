# Spec: Versions, diff & approvals

> Module M3 on `docs/ROADMAP.md`. Scope source: SPEC §21 M3; versions/diff/re-sync SPEC §7; re-anchoring SPEC §8.3; approvals & lifecycle SPEC §9; data model SPEC §16; API sketch SPEC §17; testing SPEC §18. Lineage constraint: [ADR 0001](../adr/0001-pr-is-a-candidate-version.md). Language: CONTEXT.md. Folds in issue #70 (offset unit). Specced 2026-07-19.

## Problem Statement

A Kedge document has exactly one version, forever. Import mints it; nothing ever mints a second. So the product's entire reason to exist — **comments that survive new versions** — is unproven in the running system. An author who revises the source has no way to pull the change in; a reviewer can't see what changed since they commented; an approval can't go stale because there is nothing newer to be stale against. The substrate is all there and untouched: every version carries a projection, anchors bind per `(thread, version)`, the `anchors.state` enum already names `relocated`/`orphaned`, and the Orphaned tray renders — empty, because no version transition has ever populated it. The moat is a promise the code has never once had to keep.

## Solution

The version loop, closed. An author revises the source and clicks **Re-sync**; Kedge fetches, and if the content actually changed, lands a new immutable Document Version (content-hash-deduped, so an unchanged source is an honest no-op). Every thread's Anchor is re-found on the new text through hypothes.is's proven ladder: text that's still there stays put (`anchored`), text that moved or was lightly edited relocates (`relocated`, flagged), and text that's genuinely gone drops into the **Orphaned tray** with its original quote and one-click re-attach. Reviewers land on the latest version, can switch to any earlier one, and — if a new version arrives while they're reading — get a quiet "newer version available" banner instead of a page yanked out from under them. A **diff view** answers "what changed since I commented?" in one screen, with threads overlaid on the side they anchor to. And **approvals** are version-pinned ✓s: when a new version lands, a prior approval shows as *stale* ("approved v3 · current v5"), never silently carried forward — the reviewer re-approves after reading the diff.

## User Stories

1. As an author, I want a Re-sync button on my document, so that I can pull a source revision into Kedge as a new version without re-importing from scratch.
2. As an author, I want re-syncing an unchanged source to be a no-op ("already up to date"), so that identical content never mints a twin version or needlessly re-anchors.
3. As an author, I want a failed re-sync (source deleted, token revoked, network) to keep my current version intact and show "Sync failed — showing last good version" with a reconnect CTA, so that a bad fetch never destroys the document I already have.
4. As an author, I want re-sync to be idempotent under double-clicks and concurrent triggers, so that one revision can't produce two versions.
5. As a reviewer, I want my threads to re-anchor automatically onto the new version — staying put when the text is unchanged — so that my feedback follows the words I meant across revisions.
6. As a reviewer, I want a thread whose text moved or was lightly edited to *relocate* and be visibly flagged, so that I can trust-but-verify that it followed the right passage.
7. As a reviewer, I want a thread whose text is truly gone to become *orphaned* — out of the margin, into the Orphaned tray with my original quoted context — so that it's neither silently deleted nor wrongly attached.
8. As an author or reviewer, I want to re-attach an orphaned thread by selecting new text on the current version, so that a lost anchor is one click from home.
9. As an operator, I want every re-anchor to log `{anchored, relocated, orphaned}` counts, so that orphan rate — the product's #1 health metric — is observable and alertable.
10. As a reviewer, I want to land on the latest version by default and switch to any earlier version, so that I can read the doc as it was when a past conversation happened.
11. As a reviewer with the page open when a new version lands, I want a non-intrusive "a newer version is available" banner and never an auto-swap, so that the text doesn't move under me mid-read.
12. As a reviewer, I want a comment I post while viewing an older version to anchor to *that* version, so that my anchor is never silently rebased onto content I wasn't looking at.
13. As a reviewer, I want a diff view between any two versions with my threads overlaid on the side they anchor to, so that "what changed since I commented?" is one screen.
14. As a reviewer, I want approvals pinned to older versions to show as stale in the diff header, so that the diff tells me whose sign-off predates the current text.
15. As a reviewer, I want to ✓ Approve the current version and revoke my own approval, so that my sign-off is explicit and reversible.
16. As an author, I want an approval roster on the document header showing each approval's version and staleness, so that I can see at a glance who has signed off on what.
17. As an author, I want to move the document through its lifecycle (draft → in_review → approved → superseded), so that its status reflects where the review actually is.
18. As an author, I want approvals and lifecycle changes written to the audit log, so that sign-off history is reconstructable — the start of the enterprise audit story.
19. As a maintainer, I want anchor offsets to mean the same thing on both sides of the wire (one unit, codepoints), so that re-anchoring across versions doesn't corrupt on emoji or other astral-plane text (issue #70).
20. As a maintainer, I want the version lineage schema to already express candidate versions (ADR 0001), so that the M6 PR-URL connector slots in without migration surgery — even though M3 only ever walks the mainline chain.
21. As a security reviewer, I want every new capability (resync, approve, view-versions, diff, re-attach) behind a Policy and covered by the IDOR matrix — including reviewer-via-share — so that a share link never becomes broader access.
22. As an author, I want re-sync and re-anchoring to never depend on notification fan-out, so that a new version and its re-anchored threads persist even if downstream delivery would fail (there is none in M3 anyway).

## Implementation Decisions

**Builds on M0–M2.** Auth, workspaces, Policies, shares, the projection substrate (`plain_text` + `projection_version` per version, render-time offset annotation), anchor capture (web-owned pure core), threads/comments/suggestions, the review rail + Orphaned tray shell, the journey-pack e2e infra, and the connector contract tests (including the #71 token-revoked/reconnect path) are all in place. The version-forward columns were pre-built at M1 (`documents.lifecycle_status`/`current_version_id`/`last_sync_status`/`sync_error`; `document_versions.content_hash`/`plain_text`/`projection_version`/`source_version`; unique `(document_id, content_hash)`). **No version-landing surgery is needed — the trigger is what's missing.**

**Re-sync trigger and version landing.** `POST /documents/{id}/resync` dispatches a `ResyncDocumentJob` (`ShouldBeUnique` per document). It re-fetches through the same connector resolved from `source_type`, normalizes, hashes, and lands a version via the existing `firstOrCreate((document_id, content_hash))` — the dedup already works. **Same hash → no new version, no re-anchor, "already up to date."** New hash → new version, `current_version_id` advances, re-anchoring dispatched. **Re-sync failure is not import failure** (SPEC §5.3, §19): source-gone / token-revoked / network sets `last_sync_status=failed` + `sync_error`, **never disturbs the current version**, and surfaces "Sync failed — showing last good version" with a reconnect CTA (reusing the M1/#71 `TokenRevokedException`→reconnect handling). `documents.status=failed` stays reserved for a first import that never produced a version. Authorized by `DocumentPolicy::resync` (author/member).

**Re-anchoring: web-owned matcher, api orchestration** (confirmed 2026-07-19). The exact→fuzzy→orphan ladder is a **pure TS core beside the anchor-capture core**, reached through a new shared-secret internal endpoint `POST /internal/reanchor` that mirrors `/internal/projection`: `{anchors[], newPlainText}` → per anchor `{state, start, end, exact, prefix, suffix}`. The ladder (SPEC §8.3): (1) exact match of `exact` with `prefix`/`suffix` context → `anchored`; (2) diff-match-patch position-hinted fuzzy above threshold, within a **per-anchor timeout budget** → `relocated`; (3) no match or timeout → `orphaned` (fail-safe). A `ReanchorThreadsJob`, dispatched only when a new version actually lands, **batches all the document's current-version anchors into one call** and persists a **new anchor row per thread** bound to the new `document_version_id` with its state. Older versions keep their own anchor rows — per-`(thread, version)` history is immutable, so switching to an old version still renders its threads correctly. Emits `reanchor.completed{anchored, relocated, orphaned}`. Keeping the single matcher language (JS/diff-match-patch) in one place is the direct extension of the "web owns the projection substrate, single owner" rule; a PHP port was rejected to avoid a second matcher implementation and a corpus split from the M2 capture corpus.

**One offset unit — codepoints (prefactor; closes #70).** Today web capture/annotation count UTF-16 code units (JS `.length`) while api validation counts codepoints (`mb_*`) — agreement on BMP text, silent divergence on emoji, which re-anchoring's cross-version offset recomputation would turn from "capture fails → doc-level fallback" into real corruption. **Align web capture, projection annotation, and the re-anchor core on Unicode codepoints** to match the api's `mb_` semantics. This is the module's first ticket (make the change easy, then make the easy change); the golden corpus gains emoji/astral fixtures; issue #70 closes with it.

**Version lineage is candidate-capable** (ADR 0001). Add to `document_versions` a backed-enum `kind` {`mainline`, `candidate`} default `mainline` and a nullable self-FK `parent_version_id`. Re-sync builds the mainline chain (each new mainline version's parent = the prior current version); the version switcher and diff order by this lineage, not by raw id. **Only the mainline path is exercised in M3** — Candidate Version *creation* is the M6 PR-URL connector — but the schema expresses candidates now, so no migration surgery later. `DocumentVersionResource` gains the lineage fields.

**Version list, switcher, and `?version=` threads.** `GET /documents/{id}/versions` returns the lineage-ordered list. The threads endpoint gains a `?version=` parameter end to end (client `comments-client`, `ThreadController`, `CommentThreadService::listForDocument`) so switching versions loads that version's anchors and threads. Reviewers land on `current_version`; a comment posted while viewing any version **anchors to the viewed version**, not blindly to current. The "a newer version is available" banner rides the existing polling (v1 is polling; Reverb later) and **never auto-swaps** the page (SPEC §7).

**Diff view over the projection.** `GET /documents/{id}/versions/{a}/diff/{b}` returns both versions' `plain_text`, the threads/anchors per side (paginated), and approval-staleness markers for the diff header. The textual diff is **computed and rendered in web over the projection `plain_text`** — the same substrate anchors bind to, so **comment overlay placement is exact** — using the diff-match-patch already present for re-anchoring. Threads render against the side they anchor to. A prose/raw-markdown diff is deferred (plain_text chosen for overlay correctness, not readability polish).

**Approvals lite + staleness.** A new `approvals` table (`id`, `workspace_id`, `document_id`, `document_version_id`, `user_id`, `created_at`, `revoked_at`) with an `Approval` model, `ApprovalPolicy`, and the FK indexes. `POST /documents/{id}/approvals` records `(user, current_version_id)`; `DELETE /approvals/{id}` revokes one's own. **Version-pinned:** an approval is *stale* when `document_version_id != documents.current_version_id`, rendered "approved v3 · current v5" and **never carried forward** — the reviewer re-approves after the diff. Roster on the document header. **Reviewers (share participants) and members can approve**, resolved through view capability, extending the IDOR matrix's `approve` column. Every approval/lifecycle event is audit-logged.

**Lifecycle transitions.** `PATCH /documents/{id} {lifecycle_status}` walks `draft → in_review → approved → superseded`, author-controlled, no workflow engine (the enum already exists; only the default is ever written today). Audit-logged.

**No notifications, no mail.** "New version of a doc you commented on" is an M5 notification event; **M3 sends nothing** and its re-sync/re-anchor paths never block on fan-out (hard rule 6).

**The anchoring spike is M3's entry point.** Open decision #1 (P1, TODOS.md) — validate the hypothes.is `dom-anchor-text-quote` + diff-match-patch ladder on 2–3 real RFCs before committing the full ladder — is the first re-anchoring ticket's validation step. Dogfood it on Kedge's own `SPEC.md` across its git history (real edits: moved sections, reworded sentences, deleted paragraphs), per the dogfooding principle.

## Testing Decisions

The three M2 seams, extended (confirmed 2026-07-19). Good tests assert external behavior — what re-anchoring returns, what persists per version, what renders in the rail and diff — never matcher internals.

1. **Web pipeline seam (Vitest) — the re-anchoring golden corpus = the moat's regression net** (SPEC §18.1). `(anchors captured on version A, plain_text of version B)` → expected `{state, start, end}` per anchor, covering moved sections, duplicated sentences, deleted paragraphs, and edits inside the quote — plus **codepoint/emoji fixtures** proving the #70 offset-unit fix. Mirrors and reuses the M2 capture-corpus pattern; dogfoods real `SPEC.md` version pairs. The diff renderer's overlay-placement is a pure function tested here too.
2. **API HTTP seam (PHPUnit).** Re-sync lifecycle (idempotent no-op on identical hash; new version + advanced `current_version_id` on change; failure keeps the current version and surfaces reconnect; `ShouldBeUnique` under concurrent triggers); `ReanchorThreadsJob` persistence (states written, one anchor row per thread per new version, old rows untouched, `reanchor.completed` emitted); version list + `?version=` threads; diff endpoint payload + staleness markers; approvals (record/revoke, version-pinning, stale computation); lifecycle transitions; and the **IDOR matrix's new columns** — `resync / approve / view-versions / diff / re-attach` × role, including **reviewer-via-share**. Connector re-sync reuses the recorded-fixture contract tests, including token-revoked (#71).
3. **E2E journey pack (Playwright).** Re-sync survival (SPEC §18.7): change the source → re-sync → assert one thread stays `anchored`, one `relocated`, one `orphaned` → re-attach the orphan from the tray. Approval staleness across versions. Diff view with comment overlay. Version switcher + new-version banner (no auto-swap). Real Selection APIs are exercised only here, on fixture docs; unique users/docs per spec, zero retries, M0–M2 journeys untouched.

## Out of Scope

- **Candidate Version creation / PR-URL connector** — M6. The lineage schema is candidate-capable now; no creation path ships in M3.
- **Automatic re-sync** (GitHub App push webhook, Confluence view/scheduled polling) — M6. M3 is the manual button only.
- **Notifications** (new-version emails, digests, prefs) — M5. M3 sends no mail.
- **AI / MCP** (digest consuming versions, agent participation) — M4.
- **Realtime** (live version/thread updates, presence) — polling/refresh in v1; Reverb later.
- **Required reviewers, approval deadlines, workflow rules** — deferred (SPEC §9).
- **Prose / raw-markdown diff** — plain_text diff chosen for anchor-overlay correctness; richer rendered diff is a later refinement.
- **Rail virtualization past ~200 threads** — accepted debt (TODOS.md, M2).

## Further Notes

- **Demo criterion** (SPEC §21 M3): *push a change → re-sync → comments survive or land in the tray; approval shows stale against the new version.* The re-sync-survival journey automates exactly this.
- **Orphan rate is the product's #1 health metric** (SPEC §19) — `reanchor.completed` powers it; a spike means the moat is broken → alert on it.
- **Issue #70** folds into the offset-unit prefactor ticket and closes with it. **Issue #55** (import-retry pending flag not resetting on deterministic re-failure) is the same bug class the new Re-sync button must avoid — fix it alongside the re-sync UI and close it.
- **Deployment carry-overs** (not code in this module): the preview still needs `MAIL_*` SMTP (M2 item 12A) for full dogfooding; and re-syncing a *private* source on the preview is blocked by the GitHub org IP allow list against the home egress IP — the proper fix is the M6 GitHub App, with allow-listing the egress IP as the interim (separate ops thread).
- **Next gate:** `/plan-eng-review`. The load-bearing decisions to challenge are the **candidate-capable lineage schema** (`kind` + `parent_version_id` — is this the minimal forward-compatible shape, or is a mainline sequence number enough?) and the **diff substrate** (plain_text vs a prose/markdown diff). The re-anchoring ownership (web) and offset unit (codepoints) are already decided.
