# Spec: Projects & tracked repos

> Module M3.6 on `docs/ROADMAP.md` (workspace UX wedge, decided 2026-07-21). Scope source: SPEC §21 M3.6; connector table §5.1; projects §11; data model §16; API sketch §17. Language: CONTEXT.md (**Project**, **Tracked Repo** — term pinned 2026-07-21, superseding the `repo source` working name). Builds directly on M3.5's shipped substrate (documents list, live rows, lean list resource); resolves the M3.5 out-of-band-liveness TODO. Specced 2026-07-21; **eng-reviewed 2026-07-21** (decisions 1A-14A folded in below).

## Problem Statement

Docs arrive in Kedge one paste at a time. A team's specs don't live as isolated URLs — they live as a directory in a repo (`docs/`, `rfcs/`, `adr/`), and reviewing "our specs" means importing files one by one, by hand, forever. Once imported, everything lands in one flat workspace list: Kedge's own dogfood workspace mixes product spec, design doc, roadmap, and fixtures with no grouping, and a second effort's docs would interleave with the first's. There is organization pain (no container to stand for *what you're working on*) and ingestion pain (no way to say *bring in that whole directory and keep it current*). The M3.5 list made the workspace visible; it did nothing to make it organized or self-filling.

## Solution

Two nouns, working together.

**Projects** are free containers inside the workspace — what you're working on, never where content lives. Each project gets a page: description, its documents (the same live row anatomy as home), and its tracked repos. Docs attach to at most one project and move freely; unassigned docs sit in an Unfiled bucket. The home list groups by project.

**Tracked repos** make a project self-filling. Paste a repo URL, pick a ref and a path pattern, preview exactly which files match, and import them all — each file becomes an ordinary Kedge document (own file-level source, full review surface) inside the project, with import progress live on the page as rows appear and settle. Later, one click **Re-scan** diffs the repo against what Kedge holds: new files import, changed files re-sync (comments surviving via the M3 ladder), deleted files are flagged — never auto-deleted. Tracking is pull-based on purpose: Re-scan is a button in this milestone, and the M6 GitHub App's push webhook later drives the same record without redesign.

The dogfood demo is the acceptance test: add Kedge's own repo with its `docs/` pattern to a "Kedge" project and watch the project fill itself; push a new doc, Re-scan, and it appears.

## User Stories

1. As an author, I want to create a project with a name and description, so that my workspace has a container for what I'm working on.
2. As an author, I want to rename a project or edit its description, so that the container tracks reality.
3. As an author, I want to assign a document to a project (and move it between projects, and back to Unfiled), so that organization is mine to change — no doc is locked to where it arrived.
4. As an author, I want the home list grouped by project with Unfiled last, so that a two-effort workspace reads as two efforts.
5. As an author, I want each row to carry a project chip (the slot M3.5 reserved), so that a doc's home is visible anywhere the row renders.
6. As an author, I want a project page showing its description and its documents with the same live rows as home (import status, sync state, thread counts, inline retry), so that a project is a working surface, not a label.
7. As an author, I want to add a tracked repo to a project — repo URL, ref (defaulting to the repo's default branch), path pattern — using the same connector auth as single-file import (public, or the workspace PAT for private), so that tracking works exactly where importing already does.
8. As an author, I want a preview of matching files before anything imports, so that a bad glob costs one glance, not a workspace full of noise.
9. As an author, I want confirming the preview to import every matched file as its own document into the project, with rows appearing and settling live on the project page, so that bulk ingestion has the same visibility as single imports.
10. As an author, I want Re-scan to import new matching files, re-sync changed ones, and flag deleted ones — never deleting a document — so that keeping current can't destroy review history.
11. As an author, I want a re-scan with no upstream changes to be an honest no-op ("already up to date"), so that the button is safe to press on a whim.
12. As an author, I want scan progress and the last scan's outcome (per-file: imported / re-synced / unchanged / missing / failed) visible on the tracked repo's panel, so that "what did that do?" never requires guessing.
13. As an author, I want per-file failures (one bad fetch, one over-size file) to fail that file with a reason and not the scan, so that one rotten file can't block ninety-nine good ones.
14. As an author, I want a repo-level scan failure (bad ref, revoked PAT, rate limit) to surface on the panel with the recovery action (fix ref / reconnect in Settings), so that scan failures recover the way import failures already do.
15. As an author, I want double-clicking Re-scan (or racing two scans) to run one scan, so that concurrency can't double-import a directory.
16. As an author, I want to delete a tracked repo without touching its documents, so that un-tracking is reversible organization, not data loss.
17. As an author, I want docs I moved out of the project to stay where I put them on re-scan (new files still land in the tracked repo's project), so that Project stays a free container even when a repo feeds it.
18. As an author, I want a file-count cap with an explicit over-cap error at preview time, so that `**/*` on a monorepo fails loudly before importing thousands of files.
19. As a security reviewer, I want projects and tracked repos behind Policies with workspace scoping (IDOR-proven; workspace-less reviewer sessions 403), the path pattern confined to repo paths (no traversal), and scans honoring the existing SSRF/allowlist posture, so that the new surface discloses and fetches exactly what single-file import already may.
20. As an operator, I want scans logged (counts per outcome, duration) and audit-logged (who scanned what), so that bulk ingestion is observable and reconstructable.
21. As a maintainer, I want project doc lists paginated at the database with the M3.5 clamp convention, so that big projects cost what the home list costs.
22. As a maintainer, I want the scan's appearance mechanism to own the M3.5 out-of-band-liveness TODO (rows created by a scan appear without a reload), so that the one known liveness gap closes where it was scheduled to.

## Implementation Decisions

**Language** (CONTEXT.md amended this commit): a **Tracked Repo** is a workspace-owned record — repo URL + ref + path pattern — that Kedge can scan on demand to discover and import matching files into a project. *Tracked* means remembered and re-scannable, not watched: pull-based until the M6 App webhook drives the same record. A document imported by a scan keeps its own file-level Source; the tracked repo is provenance and refresh machinery, never the document's container.

**Schema** (SPEC §16 amended to match): `projects` (workspace-scoped: name — required, ≤100 chars, unique per workspace with a friendly 422 (6A) — slug, optional description, creator). `tracked_repos` (workspace-scoped: optional project target, optional integration for PAT auth, repo URL, ref, `path_pattern` (11A), last-scan status as a backed enum, scan error, scanned-at, creator, and a denormalized **last-scan report** — per-file outcomes as JSON; scan *history* is a non-goal, so the latest report suffices). `documents` gains nullable `project_id` (assignment), nullable `tracked_repo_id` (provenance; survives project moves; nulled when the tracked repo is deleted), and nullable **`tracked_path`** — the repo-relative path a scan imported it from, with a composite unique index on `(tracked_repo_id, tracked_path)` so double-import is structurally impossible; this pair is the scan diff key (1A). Unfiled is the absence of a project, not a row.

**Ref rules (2A):** a tracked repo's ref must be a **branch name** — tags and commit SHAs are rejected at preview/create with a clear error. Branches are the only ref kind that makes Re-scan meaningful, keeps per-file blob URLs floating with upstream (so the existing re-sync job works unchanged), and matches what the M6 webhook will key on.

**Pattern syntax (9A):** gitignore-style, pinned: `*` matches within a path segment, `**` matches across segments, `?` matches one character; matching is **case-sensitive** (git paths are). Implemented as a small translated-regex matcher (no dependency) with a unit matrix locking the semantics; the UI placeholder shows the syntax (e.g. `docs/**/*.md`).

**Scan pipeline** (a Service, like all import logic): resolve the ref → list the repo tree through the connector boundary (a new tracked-repo capability beside the blob connectors, sharing their auth and host posture; the GitHub API host becomes env-configurable, production-defaulted, as the test seam) → apply the path pattern, intersected with the importable-format allowlist (`.md`/`.mdx`/`.html`) → diff against the workspace's existing docs by `(tracked_repo_id, repo path)`: **new** → create document (importing) + dispatch the existing per-file import job, source set to the file's blob URL at the ref; **changed** (upstream blob sha differs from what the last import recorded) → the existing re-sync job, so re-anchoring and content-hash no-op semantics apply unchanged; **missing** → flagged in the report only, document untouched. The report records **discovery-time outcomes** (`import queued / resync queued / unchanged / missing / failed`), written atomically at scan completion — the scan job never blocks on import jobs; per-row settle visibility is the list's live-polling job (3A). Preview runs the same resolution read-only, and additionally **warns on overlap**: matched paths already held by another tracked repo in the workspace are flagged before import, since overlapping patterns mint duplicate documents (10A). One scan in flight per tracked repo, enforced by an **atomic conditional update** (claim `running` by affected-rows; no cache/lock dependency) with **stale-running recovery**: a `running` older than ~15 minutes is claimable again and the takeover is noted in the report, so a crashed worker can never wedge the record (5A). The trigger endpoint is idempotent (202) and atomically flips the record to `pending` before dispatch (amended 2026-07-21) — the server owns "a scan is queued", so panel polling never settles on a stale terminal report under an async queue. An ok scan that matched zero files renders its own "0 files matched — adjust the pattern" state, never "already up to date". Per-file report entries ride only the settled show read; index and in-flight polls carry summary counts (lean-payload rule). File-count cap enforced at preview and scan (over-cap is an explicit error naming the count). **Upstream limits are named behaviors (4A, amended post-implementation 2026-07-21):** a truncated tree listing (GitHub truncates very large repos) is an explicit repo-level scan failure — never a silent partial match. Rate-limited blob work rides the existing import job's release/retry (shas come from the tree, so the scan itself fetches no blobs); a throttled file therefore surfaces on its document row while the job retries, rather than as a report entry — better recovery than the originally-specced report semantics, recorded as the accepted form. The UI recommends the PAT for large public repos (unauthenticated API quota is 60/hr). Comment persistence never depends on any of this — scans only feed the same import/resync paths M1/M3 shipped.

**API** (SPEC §17 amended to match): projects CRUD (index/create/update; no delete in this milestone — a project with docs poses questions v1 doesn't need to answer); `PATCH /documents/{id}` accepts `project_id` (nullable) — the target project must belong to the document's workspace; a foreign project id 404s per the no-existence-leak convention, with a dedicated IDOR test (8A). Tracked repos: preview (no side effects), create (persists + first scan), scan (manual re-scan), show (record + running state + last report — the poll target), delete (docs remain; `tracked_repo_id` and blob sha are nulled but **`tracked_path` is kept** — amended 2026-07-21 — so the 10A overlap warning still sees orphaned docs and re-tracking warns instead of silently duplicating; **409 while a scan is running or pending** — re-verified atomically inside the delete, and the 5A stale bound keeps the wait finite (7A)). Policies on every route; the M3.5 list endpoint gains an optional project filter (the `?project=` param §17 already reserves).

**Prefactor (12A):** before the panel poller is built, repay the registered poller-consolidation debt — extract `usePollUntilSettled` (one cadence constant) and move RowPoller / DocumentPoller / SharedDocumentPoller onto it, with their existing e2e coverage as the regression net (the #83 retry-affordance shape). The tracked-repo panel then lands as the hook's fourth trivial consumer, not a fourth copy.

**Web**: the project page is the M3.5 home surface re-scoped — same row components, same per-row polling, same retry affordance — plus the description header and a tracked-repos panel (state, last-report summary, Re-scan, per-file outcomes expandable). While a scan runs, the page polls the tracked-repo show endpoint and materializes newly-reported documents as importing rows, which then settle through the existing per-row path — this is the mechanism that owns the M3.5 liveness TODO. Home gains project group headers (**alphabetical, Unfiled always last** — stable ordering, no reshuffling underfoot, 14A) and the row's project chip; the `?project=` API filter shipped and powers project pages, while a home filter *control* is deferred until wanted (amended 2026-07-21 — grouping already answers story 4). Assignment UI: a project selector on the document header (capability-gated like lifecycle) and on the row's project chip. The import form, when rendered on a project page, targets that project. Tracked repos have no demo/anonymous surface.

**Failure surfaces** reuse shipped idioms: repo-level scan failure → the panel shows the error with Retry-scan, plus reconnect-in-Settings when the PAT is dead (the shared retry affordance's branch logic, generalized to scans); per-file failures land in the report and, for created-then-failed docs, in the ordinary failed-row treatment. The `/reconnect/i` prose contract is a registered debt — if the structured `sync_error_code` lands first, scans adopt it; otherwise they inherit the regex with the same debt note.

## Testing Decisions

Three seams, agreed 2026-07-21 (one new test-only knob):

1. **API PHPUnit feature tests** (existing seam; prior art: the M3.5 list matrix, the connector contract tests): projects CRUD + policy/IDOR matrix (cross-workspace, workspace-less 403); document assignment incl. the moved-doc-stays rule; preview/create/scan/show/delete with faked GitHub tree+blob responses; scan outcome matrix (new/changed/missing/failed-file/no-op re-scan); concurrency guard; file-count cap; pattern confinement; report shape. **Review-added cases (13A):** `(tracked_repo_id, tracked_path)` uniqueness; tag/SHA ref rejection; report-is-discovery-outcomes atomicity; truncated-tree → repo-level error; rate-limited blob → per-file failure with reason; concurrent scan claim (exactly one winner); stale-running recovery + takeover note; DELETE-while-running 409; project name required/≤100/unique 422; foreign-project assignment 404 (IDOR); pattern matrix incl. `*`-vs-`**` segment semantics and case sensitivity; preview overlap warning. Scan correctness is proven here — it's the cheapest seam with full control of upstream state.
2. **Web vitest** (existing seam; prior art: `document-list-live`): scan-report → row materialization projection, poll predicates, static-markup states for the project page and tracked-repo panel (running, failed, PAT-dead, over-cap, empty project); `usePollUntilSettled` unit tests, with the three existing poller consumers' e2e coverage as the prefactor's regression net (12A/13A).
3. **Journey pack** (existing seam + the new knob; prior art: `FETCH_ALLOW_HOSTS`, the fixture host, M3.5's poll-parking determinism pattern): the GitHub API host env-configurable so serve-fixtures emulates the minimal tree/contents endpoints; **one journey**: create project → add tracked repo with a pattern → preview shows the fixture repo's files → confirm → rows fill the project live → mutate the fixture → Re-scan → the new doc appears and a changed doc re-syncs. Deterministic via poll-parking, not timeouts.

Good tests here assert external behavior — what the workspace contains and shows after a scan — never the scan's internal ordering. The golden re-anchoring corpus already guards the re-sync half; these tests only need to prove scans *reach* it.

## Out of Scope

- **Push/webhook watching** — M6's GitHub App drives the same tracked-repo record; nothing here may preclude that, nothing here builds it.
- **Confluence spaces** (M6), **generic git hosts** (Later), **local-directory daemon** (fog — v1 is pull-based).
- **Project sharing/permissions and References** (post-v1, per the 2026-07-15 language decision); project deletion; project-level approvals or lifecycle.
- **Scan history** (only the last report persists); **rename/move detection** (a moved file is a missing flag + a new doc in v1); **cross-tracked-repo dedupe** of identical content.
- **Retroactive adoption** — a previously hand-imported doc whose URL matches a scan's file is not claimed by the tracked repo in v1 (it would double-import; the dedupe question is registered debt with the duplicate-import entry).
