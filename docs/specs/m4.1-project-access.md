# Spec: Project access

> 2026-09-26 · M4.1 · Status: specced; engineering/design review pending.
> User-confirmed: scope, testing seams, roles, membership administration, source
> authority, AI access, document sharing, removal semantics, and document moves.
> See the decisions below. Detailed content/moderation and invitation lifecycle
> remain draft defaults pending user input.

## Problem Statement

An owner has a project containing the documents a colleague needs to review,
but cannot invite that colleague into the project. Individual document links
require repeated sharing, do not provide a project home, and do not establish a
manageable role. There is no roster, pending-invitation view, or way to remove
someone's project access. The app's personal-workspace assumption also means
that adding a membership record alone would not let the invitee find the work.

## Solution

Add project membership with email invitations and three roles: **Viewer**,
**Reviewer**, and **Maintainer**. An invitee accepts with a verified full account
and finds the project under **Shared with you**. Access covers the project's
current and future documents, including their versions and discussions. It does
not expose other projects, Unfiled documents, workspace settings, or credentials.

A project's **Members** screen shows the workspace owner, project members, and
pending invitations. Authorized users invite, resend, revoke, change roles, and
remove members. Removal preserves review history while ending the removed
grant's authority. Existing document shares remain separate grants.

Keep workspace ownership and project membership distinct. Later workspace
invitations can reuse the invitation lifecycle and capability evaluation while
granting access at a broader scope to the same accounts.

## User Stories

1. As a workspace owner, I want to invite a colleague to one project by email,
   so that they can review it without seeing unrelated work.
2. As an inviter, I want to select Viewer, Reviewer, or Maintainer where allowed,
   so that access matches the recipient's responsibility.
3. As an inviter, I want the default role to be Reviewer and the form to explain
   that access includes current and future project documents.
4. As an existing user, I want to sign in and explicitly accept an invitation,
   so that someone cannot silently add projects to my account.
5. As a new user, I want to register, confirm my email, and return to acceptance,
   so that onboarding does not lose the project I was invited to.
6. As an invitee signed into a different account, I want a clear account-switch
   path without accepting under the wrong identity.
7. As a magic-link Reviewer, I want to upgrade to a verified full account through
   the existing registration flow while retaining my review attribution.
8. As an invitee, I want opening or previewing an email link to leave membership
   unchanged, so that mail scanners cannot accept on my behalf.
9. As an invitee, I want an expired, revoked, or replaced link to explain why it
   cannot be accepted and direct me back to the inviter.
10. As a project member, I want Shared with you to show the project and its owning
    workspace, so that identically named projects remain distinguishable.
11. As a project member, I want my personal workspace to remain available and
    unchanged when I enter someone else's project.
12. As a Viewer, I want to read documents, versions, diffs, and discussions with
    no controls suggesting that I can change them.
13. As a Reviewer, I want to comment, reply, react, suggest edits, and approve a
    version, so that I can participate in the review.
14. As a Reviewer, I want to manage my own review contributions while my current
    role allows it, without editing or moderating someone else's words.
15. As a Maintainer, I want to triage reviews, update lifecycle, and replace
    pasted/uploaded content, so that I can run the project without its owner.
16. As a Maintainer, I want to add pasted/uploaded documents directly to the
    project, so that my personal workspace does not become their accidental home.
17. As a Maintainer, I want to import URLs, add/remove tracked repos, choose
    branches/path filters, and run re-syncs/scans within my project's approved
    source access, without receiving workspace credentials.
18. As a workspace owner, I want to approve private repositories for each
    project, so that Maintainers can manage sources without accessing every
    repository my workspace credential can reach.
19. As a Maintainer, I want to invite and administer Viewers and Reviewers, while
    only the workspace owner can grant or change Maintainer seats.
20. As an owner, I want to see pending invitations, expiry, and delivery status,
    then resend or revoke them without creating duplicate memberships.
21. As a project member, I want to see names, roles, and the origin of access,
    without exposing invitation email addresses to everyone in the project.
22. As a project member, I want to leave a project without deleting my historical
    comments, suggestions, or approvals.
23. As an owner, I want removal and downgrades to stop later unauthorized writes,
    including work already queued by the affected person.
24. As a Maintainer of both projects, I want to move a document between them;
    as the workspace owner, I also want moves to/from Unfiled. Each move explains
    the new audience and applies it to the document's entire version history.
25. As an owner, I want removal to explain that existing document share links
    remain usable independently, so that I do not mistake it for revoking them.
26. As a project member, I want mention suggestions, counts, and source metadata
    limited to what I can access, without learning about other workspace work.
27. As a Reviewer, I want Ask and reply drafts to help me review; as a Maintainer,
    I also want the broader AI tools for the project. Personal drafts/questions
    remain private to their author.
28. As an owner, I want project invitations to grant no additional MCP token
    authority, so that human membership cannot widen an agent's scope.
29. As a self-hoster, I want invitations to work through configured SMTP and the
    database queue with no SaaS-only dependency.
30. As a keyboard or mobile user, I want membership flows to work in both themes
    and every supported UI locale.
31. As a future workspace administrator, I want workspace grants to compose with
    existing project grants without migrating users or losing membership history.

## Implementation Decisions

### Scope, terms, and draft defaults

The module is one vertical capability spanning API authorization, invitations,
account onboarding, discovery, and member management. Workspace membership UI,
teams, and private-project exceptions to workspace access remain later scope.

A **Project Member** holds a direct project grant. A **Reviewer** role on that
grant is not the existing passwordless magic-link Reviewer identity. Acceptance
requires a full account with a verified email; it creates no workspace-member
record and never changes a user's personal workspace.

**Confirmed 2026-09-26:** Viewer, Reviewer, and Maintainer, with Reviewer as the
invitation default. Maintainers may invite, change roles, and remove Viewers and
Reviewers. Only the workspace owner may appoint, demote, or remove Maintainers.
Any member may leave their own direct project membership voluntarily. Maintainers
can manage project sources, including branches/path filters; private repository
access is limited to repositories the workspace owner approves for that project.
Credentials and repository approvals remain owner-controlled. Reviewers may run
Ask and reply drafts; Maintainers may run all existing AI tools. Viewers may read
shared results but cannot start generation. Personal questions/drafts stay private.
Maintainers may create, list, and revoke document share links for their project;
Viewers and Reviewers gain no share-management capability. Removal ends the
direct project grant immediately, preserves comments/suggestions/approvals, and
leaves independent share links active until explicitly revoked. The removal
flow explains remaining share access and offers link review/revocation.

Maintainers may move documents between two projects in the same workspace when
they are Maintainer in both. The workspace owner may also move to/from Unfiled.
Cross-workspace moves remain out of scope.

Remaining draft defaults for review: invitations expire after seven days; the
detailed invitation lifecycle and content/moderation rules below remain for review.

### Capability matrix

The following are **direct project-grant** capabilities. The owning workspace's
owner inherits every project administration capability. Existing workspace
member capabilities continue to apply independently; a lesser direct project
role does not subtract an existing workspace grant.

| Action | Viewer | Reviewer | Maintainer |
|---|---|---|---|
| Read project, documents, versions, diffs, and threads | Yes | Yes | Yes |
| Read project roster: names, avatars, roles, access origin | Yes | Yes | Yes |
| Read shared AI artifacts for accessible documents | Yes | Yes | Yes |
| Comment, reply, react, suggest, approve current version | No | Yes | Yes |
| Edit/delete own comments, remove own approval | No | Yes | Yes |
| Resolve/reopen/fork own threads; reattach own anchored threads | No | Yes | Yes |
| Resolve/reopen/fork/reattach any project thread | No | No | Yes |
| Delete another person's comment; accept/decline suggestions | No | No | Yes |
| Edit another person's comment text | No | No | No |
| Update project name/description and document lifecycle | No | No | Yes |
| Add pasted/uploaded documents; replace their content | No | No | Yes |
| Retry/re-sync existing documents; re-scan attached repos | No | No | Yes |
| Read attached source configuration and scan reports | No | No | Yes |
| Import public URLs and manage tracked repos within approved source access | No | No | Yes |
| Approve private repositories or manage their credentials | No | No | No |
| Create/list/revoke document share links | No | No | Yes |
| Generate Ask answers and reply drafts, subject to existing limits | No | Yes | Yes |
| Generate digests, improve-prompts, summaries, and split proposals | No | No | Yes |
| Invite/change/remove Viewers and Reviewers | No | No | Yes |
| Invite/change/remove Maintainers | No | No | No |
| Move between projects in the same workspace | No | No | Maintainer in both |
| Move to/from Unfiled | No | No | No |
| Leave own direct project membership | Yes | Yes | Yes |
| Manage workspace settings, integrations, or MCP credentials for it | No | No | No |

The owner-only actions above are unavailable through a project grant, regardless
of who originally created the document. A Maintainer cannot demote/remove a peer
or alter a pending Maintainer invitation. Self-service leaving removes only the
actor's direct grant, including a Maintainer's. Inherited owner access cannot be
removed from the project screen.

Moderation preserves attribution: another person's comment may be deleted by a
Maintainer, not rewritten as if its author had said something different. Apply
that rule consistently to workspace owners on project documents as well.

### Authorization composition and revocation

Keep Laravel Policies as the gate on every resource route. Introduce a shared
capability resolver and matching database query scopes for project access;
controllers validate, authorize, and delegate. Do not equate read access with
write access or add project memberships to the existing workspace-member test.

Human capabilities are the union of current workspace-derived and direct
project grants. Document share grants remain on the existing share surfaces.
MCP additionally requires the existing workspace membership and credential
scope; a project grant alone is never sufficient for MCP. Future workspace
roles can contribute capabilities through the same resolver without changing
project grants. This release adds neither workspace invitations nor a generic
ACL framework.

For documents in projects, document/thread/comment authorship alone no longer
grants access or mutation rights after removal, a move, or a role downgrade.
Own-contribution actions also require the current role's review capability.
This deliberately revises the old surviving-authorship behavior. Unfiled
workspace-member capabilities and active share-reviewer behavior remain intact,
but authorship must require live document reach there too: moving a document to
Unfiled cannot carry a former project member's author privileges into the
workspace. Ownership metadata remains attribution, not an access grant.

Membership changes, invitation acceptance, document moves, and project-authorized
writes serialize on a stable project access guard inside short transactions.
Re-resolve the actor's live grant and resource's current project at commit. Use
deterministic lock ordering for moves involving two projects, and the document
row to serialize moves with its writes. Removed grants are never honored from
an earlier request snapshot. PostgreSQL row locking and SQLite write-transaction
serialization must both satisfy the behavior; do not claim SQLite row locks.

After removal/downgrade returns successfully, no later database mutation may
commit using the superseded grant. Reads begun afterward must reauthorize;
already delivered or in-flight response bytes cannot be recalled. Do not cache
membership across requests. The web discards stale responses after access loss
and renders an access-removed state instead of redirecting a signed-in user
into a sign-in loop.

Queued work records the initiating user and direct grant identity/version when
project access authorized it, including descendant import/re-sync/AI jobs.
Re-check before starting external work and before committing content/results;
membership removal, downgrade, or source reassignment invalidates that queued
authority even if the user is later re-invited. Work already sent to an external
service cannot be recalled or unbilled; its result must not commit through an
invalid grant. Affected runs/scans use their existing terminal failure state
with an `access_revoked` reason; a first import fails, while a re-sync keeps its
last good version. Administrative cleanup may settle those states after grant
loss but may not publish new content or AI output. No work remains running/
importing forever. Workspace-owned automated work retains its separate
authorization; removal does not stop all project jobs.

### Membership and invitation persistence

Use explicit project-membership and project-invitation records with foreign keys
to the project, owning workspace, and relevant users. Project membership is
unique per project/user and carries a backed-enum role, grant version, and join
timestamps. Enforce the project/workspace relationship, not just independently
valid IDs. Index every lookup/join column explicitly; lists paginate at the
database and eager-load identities.

An invitation records normalized recipient email, offered role, inviter, token
digest, token generation, expiry, lifecycle state, accepted user/grant, delivery
state, and timestamps. Maintain one current invitation slot per project/email;
resend or a later re-invitation replaces its token/generation, while audit events
retain the historical actions. States are pending, accepted, revoked, and expired;
delivery queued/sent/failed is separate. No permission derives from a pending row.

An accepted membership and the accepted invitation transition commit atomically.
Concurrent acceptance produces one membership. An existing member is never
silently promoted by invitation or replay: invite returns a member-already-exists
conflict and directs the administrator to the role-change action.

The service boundary separates invitation lifecycle (issue, resend, revoke,
preview, accept, deliver) from scope-specific authority and grant creation.
Later workspace invitations can use their own explicit workspace foreign keys
and membership records behind that lifecycle. Do not use a polymorphic target
without database integrity merely to anticipate future scopes.

### Invitation lifecycle, identity, and delivery

- Issue a cryptographically random token with at least 256 bits of entropy;
  persist its digest, not plaintext. Tokens, full links, and sensitive mail
  bodies must be redacted from request/audit/error telemetry. Queue payloads
  carrying the delivery token are encrypted, including failed-job storage.
- Expiry is seven days after issuance. Resend rotates the token/generation and
  restarts expiry. Apply a sixty-second resend cooldown and configurable
  per-user/project and per-workspace rate limits to invite/resend operations.
  Duplicate pending invitations do not send another email or change role.
- GET preview discloses only the project's name, inviter display name, offered
  role, masked recipient, and expiry to the link holder. It grants no session,
  email verification, or membership. Never expose document counts or content.
  Invalid links get a uniform invalid-link page; recognized expired/revoked
  links may show their recovery state without revealing further project data.
- Acceptance is an authenticated, CSRF-protected POST by a verified full account
  whose normalized email exactly matches the recipient under existing account
  normalization. No provider-specific dot/plus alias guessing. Wrong account
  receives an account-switch action and no mutation.
- Preserve an internal-only acceptance destination through password login,
  registration/email confirmation, and GitHub login. OAuth's verified email must
  still match. Reuse existing account upgrading and fresh mailbox-proof rules
  for magic-link reviewer identities; possession of an invitation is insufficient.
- In one transaction, verify token generation, expiry, recipient, project, and
  inviter's current authority to grant the offered role, then create membership
  and mark accepted. A retry by the same accepting account returns the existing
  membership without reapplying the invitation role. After membership removal,
  replay returns no-longer-active and never recreates access.
- Revocation or loss of the inviter's invite authority invalidates their pending
  invitations. Enforce both when authority changes and at acceptance; later
  restoration of the inviter's membership cannot revive an old invitation.
  Role changes on pending invitations use revoke plus a fresh invitation.
- Queue mail after the invitation transaction commits through the configured
  Laravel transport. Delivery workers verify generation, pending state, expiry,
  and inviter authority before sending; stale jobs do not send superseded links.
  Sent means transport accepted, not proof of inbox delivery. Transport failures
  use bounded retries and then show Failed with resend recovery. Dispatch failure
  also leaves a recoverable invitation state. A mail failure grants nobody access
  and never rolls back an unrelated comment or review action.

### Discovery, API contracts, and data minimization

Keep the personal-workspace home, summary, activity feed, settings, and existing
unfiltered lists scoped as today. Add a separate paginated Shared with you project
list; do not widen a personal-workspace query to include unrelated workspace rows.
Each invited-project item includes safe workspace identity (name and ID), the
project, effective capabilities, and access origin. An owner already discovering
their project through the personal workspace need not see it duplicated here.
Use the existing page/per-page convention and clamp for new list endpoints.

Add these contracts under the existing versioned API:

| Operation | Contract |
|---|---|
| Shared-project discovery | `GET /me/shared-projects` |
| Direct project read | `GET /projects/{project}` |
| Roster | `GET /projects/{project}/members` |
| Change direct role | `PATCH /projects/{project}/members/{user}` with role |
| Remove/leave direct membership | `DELETE /projects/{project}/members/{user}` |
| List/issue invitations | `GET` / `POST /projects/{project}/invitations` |
| Resend | `POST /projects/{project}/invitations/{invitation}/resend` |
| Revoke | `DELETE /projects/{project}/invitations/{invitation}` |
| List approved repositories (owner/Maintainer) | `GET /projects/{project}/repository-approvals` |
| Approve a repository (owner only) | `POST /projects/{project}/repository-approvals` |
| Withdraw approval (owner only) | `DELETE /projects/{project}/repository-approvals/{approval}` |
| Change tracked branch/path filter (owner/Maintainer) | `PATCH /tracked-repos/{trackedRepo}` |
| Preview acceptance | `GET /project-invitations/{token}` |
| Accept | `POST /project-invitations/{token}/accept` |

Authenticated resource routes retain verification, session/CSRF, throttling, and
the agent-bearer refusal. Preview alone is available without an account and is
rate-limited. Invitation responses carry no plaintext token; delivery uses mail.
Creation returns 201 with delivery state; acceptance returns 200 with project
destination and membership; removal/revoke return 204. Missing/unreachable new
project resources share a 404; visible but forbidden actions return 403. Validation
is 422, lifecycle conflicts 409, inactive recognized acceptance links 410, and
throttling 429. No cross-project nested-ID binding or count disclosure.

Existing document and tracked-repo list endpoints with an explicit project
filter authorize that project and scope to it. Unfiltered and Unfiled reads stay
personal-workspace scoped. Tracked-repo configuration/report reads additionally
require source-management capability. Document import with a project ID resolves
the owning workspace from that authorized project; an omitted project keeps the
existing personal-workspace behavior. Never trust a supplied workspace ID.

Resource capabilities govern controls individually: comments, approvals,
moderation, lifecycle, content, import/re-sync, source reports, AI, sharing, and
membership actions. Missing capabilities fail closed during additive rollout.
Project-only Viewer/Reviewer payloads omit integration identifiers, configured
repo/path/ref details beyond ordinary document provenance, raw scan reports,
and internal import errors. Source grouping may use a safe project-local label
and reference without exposing the full tracked-repo resource.
The direct project read supplies those safe source groups, so Viewer/Reviewer
pages can retain the existing grouped document layout without fetching a
Maintainer-only source configuration endpoint.

Roster reads expose names/avatars/roles and access origin, not emails. Invitation
administrators can see pending recipient emails and delivery state; Viewers and
Reviewers cannot list pending invitations. Mention suggestions and server-side
mention validation use eligible participants in the accessible document/project,
not a directory of the workspace. Historical authors remain attributed but are
not mentionable merely because they once contributed. No project-only access to
workspace audit feeds, aggregate summaries, integration metadata, or token lists.

### Documents, sources, AI, shares, and audit

Project membership covers all current project documents and their entire version
history, including later candidate versions of the same Document. It creates no
copies and does not alter the existing candidate-version domain decision.

**Source authority confirmed 2026-09-26:** Maintainers may paste/upload documents,
import public URLs, add/remove tracked repos, change tracked branches/path filters,
and run imports/re-syncs/scans. Authenticated repository access is limited to
repositories the owner explicitly approves for this project. Approval covers the
repository; Maintainers need no further owner approval for branches or paths
within it. Existing supported-ref, connector, file-cap, and SSRF rules still apply.

A **Repository Approval** binds one project to a canonical repository and an
owner-selected workspace integration. Store owning workspace/project/integration
foreign keys, canonical provider/repository identity, approving owner, grant
version, and revocation state/timestamps, with explicit lookup indexes and a
unique current grant per project/repository. Validate the repository identity
through the connector when the owner approves it. Maintainers select approved
repository identities, never arbitrary integration IDs or credentials. Approval
for one project does not grant another project access to the repository.

The project's source area gives the owner an Approved repositories control and
Maintainers a picker containing only current approvals. Owner setup may use the
existing connected integration; Maintainers cannot browse its complete repository
inventory. Public URL/repo imports without an approval are credential-free:
never silently retry with the workspace PAT. Private imports, previews, scans,
re-syncs, and descendant jobs all resolve the same approval before credentialed
fetches and revalidate its version before committing results. Canonical identity,
redirect handling, and credential forwarding must not permit a URL spelling or
redirect to substitute an unapproved repository.

Revoking approval stops subsequent Maintainer-authorized credential use, including
queued work under its previous version; it preserves imported documents and their
review history. Show source access withdrawn with owner recovery instead of a
perpetual retry. The workspace owner's independent authority remains. Credential
rotation within the same integration does not broaden the approved repository;
substituting another integration requires owner action. Existing connected repos
are not automatically approved for delegation: the owner explicitly enables each
repository for the project before a Maintainer may use its credentials. A moved
private-source document similarly requires approval in the destination project
for Maintainer re-sync, while read access follows its document membership rules.

Tracked-repo edits use the existing branch/path validation and preview before
saving. They are refused while a scan is pending/running; scans bind to a stable
configuration version, so an old job cannot apply results from a replaced config.
Changing the repository identity uses remove/add under the new repository's
approval. Removing a tracked repo uses the existing untrack behavior: documents
and reviews remain. Narrowing a path filter never deletes imported documents.
This adds source management, not document deletion or arbitrary replacement of
a document's origin. Source-approval changes are audited without secrets.

**Document moves confirmed 2026-09-26:** a Maintainer may move a document between
projects only if they are Maintainer in both the current and destination projects
and both belong to the same workspace. The workspace owner may move documents
anywhere within that workspace, including to/from Unfiled. The move picker lists
only authorized destinations; the API independently checks both ends again at
commit, including concurrent role changes. A move cannot bypass either project's
authority by being bundled with a lifecycle update.

The action names the destination audience before confirmation and changes access
for all versions/threads/approvals atomically. Existing independent document share
links retain their separate access; the confirmation explains that a move does
not revoke them. Preserve the
existing rule that tracked documents may move freely without losing provenance:
a scan never reassigns an existing document to its tracked repo's project.
Maintainer-triggered scans skip existing documents outside that Maintainer's
current authority, without reimporting them as duplicates. The skip is enforced
again by descendant jobs; a move during a scan cannot bypass it. Source reports
and their aggregates omit outcomes for documents outside the reader's access.
Owner-triggered scans retain their workspace-wide authority. No cross-workspace
moves or project deletion are added.

**AI access confirmed 2026-09-26:** Reviewers may generate Ask answers and reply
drafts. Maintainers may also generate digests, improve-prompts, thread summaries,
and split proposals. Viewers cannot start generation. All three roles may read
shared document-scoped results. Existing feature gates and rate limits apply;
costs use the owning workspace's configured provider and are attributed to the
initiating user. Invitation/role-change copy explains AI use for Reviewer and
Maintainer roles. Generated output remains a draft; generation grants no extra
permission to post, moderate, or apply it.

Ask/reply-draft artifacts retain per-actor privacy in addition to current project
reach. Authorization and returned capabilities distinguish run types, not merely
"AI enabled" or "project member". A downgrade removes newly forbidden generation
capabilities and invalidates queued work under the previous grant version; it
never exposes private drafts to others. Project membership still grants no new
MCP authority: minting a token for the owning workspace or using personal tokens
against the invited project remains outside this module.

**Document sharing confirmed 2026-09-26:** Maintainers may create, list, and revoke
share links for documents currently in their project, including links created
by another authorized person. Existing workspace-authorized actors retain their
capabilities; Viewers and Reviewers gain no share-management capability. Reuse
the existing document-level share flow, expiry, visibility modes, and reviewer
identity rules. A project grant never turns into a workspace-wide share grant.
Moving a document or losing the Maintainer role re-evaluates share-management
authority against the document's current project.

**Removal semantics confirmed 2026-09-26:** removal immediately ends the direct
project grant, including authorship-based access through that grant. Preserve
comments, suggestions, and approvals. Independent document shares and workspace
grants remain valid. Explain remaining grants in the removal result and offer
authorized administrators the existing share-management entry point to review
and explicitly revoke links; never automatically revoke unrelated links. Shares remain a separate access path
even for a person whose project role is Viewer or whose membership was removed.

Audit invitation issue/resend/revoke/accept, role changes, leaving/removal, and
document audience changes with actor, target, scope, and old/new role as relevant.
Never record tokens or full links. Grant creation/escalation and their audit event
are atomic. Access reduction must still take effect if the audit sink fails,
using the established safe audit/error-reporting pattern. Public activity
projections must not expose recipient emails or invitation metadata.

### UX, rollout, and delivery boundaries

Members opens from the project header. Use the approved panel/form vocabulary,
Tailwind utilities, local display font, both themes, and existing four locales.
Show inherited owner access distinctly. Invite forms show only grantable roles;
row controls follow per-target capabilities. Pagination, keyboard focus, labelled
errors, and narrow-screen layouts are required. No full workspace switcher is
needed: the project header labels its workspace and links back to Shared with you.

Acceptance offers an explicit Join project action after identity checks, then
opens the project. Show clear expired/revoked/replaced, wrong-account, sending,
delivery-failed, empty-roster, and load-failed states. The removal dialog explains
that contributions remain and separate shares may still grant document access.
Role-change copy states newly granted powers, including AI use for Reviewer
and Maintainer, with the specific tools available to each.

Use additive migrations and deploy API before web. Existing projects inherit owner
access without synthetic invitations or per-project owner backfills. Preserve
the personal-workspace session response. New client controls fail closed against
an older API. Ship invitations only once all reachable API actions and queued
work honor the capability matrix; a partially protected collaboration flow must
not become available between vertical slices.

   effects, expiry/replay, duplicate invitations, resend token rotation, invalid
   inviter authority, removed/re-invited grants, mail/dispatch failure recovery,
   encrypted delivery payloads, and secret-free resources/audit. Execute queued
   jobs across revocation/downgrade boundaries and assert no unauthorized result
   commits or indefinitely running states. Exercise additive migrations against
   existing personal workspaces with zero membership backfill assumptions.
3. **Database concurrency check.** Follow the existing MCP revoke/write test
   pattern with committed fixtures and independent connections. Assert acceptance
   versus revoke, duplicate acceptance, role downgrade versus write, and document
   move versus write; the losing operation cannot activate or persist forbidden
   work. Require a PostgreSQL-backed run for row-lock behavior and a file-backed
   SQLite run for write-serialization behavior. In-memory SQLite or a skipped
   locking test is not evidence for either concurrency guarantee.
4. **Playwright journey seam.** Two account contexts: owner invites an existing
   user, user accepts and finds the project, reviews a document, fails to reach a
   sibling project, then loses access on removal. A second journey covers new
   signup/email confirmation and return to acceptance, including wrong-account
   recovery. Exercise the Viewer and Maintainer controls, pending-invite resend/
   revoke, role downgrade with stale UI, leaving, and error recovery. Read actual
   test-transport mail links as the existing auth journeys do; no direct database
   membership shortcuts for acceptance. Include keyboard/mobile, both themes,
   and translation-key parity using existing test infrastructure.

No live GitHub, AI provider, or mail vendor is used in automated tests. Before
release, confirm a real invitation email reaches a controlled mailbox through
the deployed queue/transport, then accept with a second account and remove it.
Demonstrate against Kedge's actual documentation project where practical.

## Out of Scope

- Workspace invitations, workspace membership UI, workspace role redesign,
  private-project exceptions to workspace grants, accounts, billing, teams, SSO.
- Project-scoped MCP tokens or permission to use an invitee's personal token in
  the owning workspace.
- Custom roles, per-document membership overrides, anonymous project links,
  bulk/CSV/domain-based invitations, and automatic account provisioning.
- Maintainer access to unapproved private repositories, workspace credentials,
  or repository-approval administration; cross-workspace
  document moves; project deletion/ownership transfer.
- A new notification inbox or review queue; invitation mail uses existing auth/
  transactional-mail infrastructure and does not depend on the notifications module.
- Recalling downloaded content, cancelling external calls already sent, or
  revoking independent share/workspace grants as a side effect of project removal.

## Further Notes

**Demo criterion:** an owner invites a colleague to Kedge's documentation project;
the colleague accepts, discovers it, comments and approves within their role;
another project remains inaccessible; removal ends the direct project access
without deleting the review record.

Suggested ticket boundaries: invitation/acceptance and discovery; role-aware
review and content/source actions; member administration and lifecycle recovery.
Authorization and denial tests accompany each slice, and public enablement waits
for the complete capability boundary.

The three-role model, Reviewer invitation default, membership-administration
boundary, voluntary leaving, and source management within owner-approved private
repositories are confirmed. Reviewer Ask/reply-draft access, Maintainer access
to broader AI tools, personal artifact privacy, and Maintainer document-share
management are also confirmed. Removal ends the direct grant while preserving
review history and independently active share links, with explicit link-revocation
recovery. Moves are allowed for Maintainers in both same-workspace projects;
Unfiled remains owner-only. Detailed content/moderation actions and invitation
rules remain visible review points, not evidence of separate user approval. Engineering review should focus on query/policy consistency, grant
revocation through queued work, database serialization, and additive API rollout.
Design review should walk the acceptance, role-change, and access-loss journeys.
After those gates, create the vertical-slice tickets.
