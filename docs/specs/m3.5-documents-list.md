# Spec: Documents list

> Module M3.5 on `docs/ROADMAP.md` (workspace UX wedge, decided 2026-07-21). Scope source: SPEC §11 ("Your docs" half, pulled forward from M5), §21 M3.5; API sketch §17 (`GET /documents`); testing §18. Language: CONTEXT.md. Decision context: TODOS.md decision log 2026-07-21. Specced 2026-07-21; **eng-reviewed 2026-07-21** (decisions 1A–10A folded in below).

## Problem Statement

A workspace can hold any number of documents, but the authenticated home renders a greeting and an import box — nothing else. Every doc a user has ever imported is reachable only by remembering its URL or replaying browser history. Import is asynchronous, and each document's progress is visible only on its own page; kick off three imports and there is no screen that shows how any of them are doing. The M5 "review-queue dashboard" was going to fix this, but it is bundled with notifications for the sake of its *other* half ("Needs your attention") — the "Your docs" half has no notification dependency at all, and waiting two milestones to see your own documents is dogfooding pain today.

## Solution

The authenticated home becomes the workspace documents list. Under the existing import box, every document in the workspace, newest first, paginated: title, lifecycle chip, open-thread count, last-sync state and time, and — for docs still in flight — a live import status that settles in place (importing → ready/failed) without a refresh. **Submitting an import stays on the home page** (eng review 5A): the 202 response's document prepends as an importing row, which is what makes "watch three imports at once" real; the row's title link is how you reach the review surface. Failed rows show the import error and retry inline through the existing retry endpoint via a **retry affordance shared with the doc page's `ImportFailed` state** (7A) — including the M1 nuance that a dead PAT offers "reconnect in Settings", not a futile retry. M5 later stacks "Needs your attention" on top of this list; M3.6 adds project grouping to the same rows — the row anatomy is designed with a project chip slot from day one.

## User Stories

1. As an author, I want the home page to list every document in my workspace (newest first, paginated), so that nothing I import is ever lost to URL memory.
2. As an author, I want each row to show lifecycle status, open-thread count, and last-sync state/time, so that I can triage my docs at a glance.
3. As an author, I want documents that are still importing to show live progress on the list and settle to ready or failed in place, so that I never have to refresh to learn an import's fate.
4. As an author, I want submitting an import to keep me on the home page with the new doc prepended as an importing row, so that I can kick off several imports and watch all of them from this one screen.
5. As an author, I want a failed row to show why it failed and offer Retry inline — or "reconnect in Settings" when the cause is a dead PAT — so that recovery starts where I see the failure.
6. As an author, I want clicking a row to open the review surface, so that the list is the workspace's front door.
7. As an author with no documents yet, I want the list area to say so and point at the import box, so that the empty state teaches the entry point.
8. As an author, I want the home page to stay usable when the API is unreachable — import box rendered, list area degraded to the standard "API unreachable" panel — so that an API blip never bricks the front door (3A).
9. As a security reviewer, I want the list endpoint behind a `viewAny` Policy (personal-workspace holders only — a magic-link reviewer gets 403, never a 500) with the query explicitly scoped to that workspace and paginated at the database, so that it discloses exactly what `GET /documents/{id}` would allow, page by page (1A).
10. As a maintainer, I want the row payload lean by construction — a dedicated list resource, no document content, no per-row capability checks — so that the home page cost stays flat as a workspace grows (6A).
11. As a maintainer, I want only rows in `importing` state to poll — each through the existing per-document BFF route — and to stop the moment they settle, so that an idle home page issues zero background requests (2A).
12. As a screen-reader user, I want a row's settle announced (`aria-live="polite"` on the status region) and rows/retry reachable as real links and buttons, so that watching an import is not sight-only (10A).
13. As a maintainer, I want an e2e journey that imports from home and watches the row settle to ready, so that the list's liveness — its whole point — is regression-guarded.

## Implementation Decisions

**API.** New `GET /api/v1/documents` (`DocumentController@index`):
- **Authorization (1A):** add `DocumentPolicy::viewAny` = `hasPersonalWorkspace` (mirrors `create`); the controller authorizes it *then* scopes the query to `$user->personalWorkspace()->documents()`. Policies authorize; the query scopes — both are explicit. A workspace-less user (magic-link reviewer) gets 403, never a null-dereference 500. System-workspace demo docs are excluded structurally by the scope (asserted, not assumed).
- **Pagination (4A):** page-based, `per_page` clamped `min(max(n, 1), 50)`, default 20 — the same clamp as `CommentThreadService::listForDocument`. `latest()` order.
- **Payload (6A):** a new lean `DocumentListResource`: `id, title, status, last_sync_status, sync_error, lifecycle_status, open_threads_count, synced_at, created_at`. `synced_at` comes from a select-limited eager load of `currentVersion` (`id, document_id, synced_at` only — `DocumentResource`'s `current_version` carries full content and must not be reused here). No `capabilities` block, no approvals roster: the row is read-only navigation. One more hand-synced TS shape, accepted under the registered OpenAPI-codegen debt.

**Web.**
- `ReviewQueue` on `app/page.tsx` grows the list under the import panel (inside the existing `PageContainer`). Server component fetches page 1 via a new BFF route (`GET /api/bff/documents`, same `forwardApiGet` pattern); a client island owns prepend-on-submit, per-row polling, and "Load more" (appending, in-flight-guarded against double-clicks).
- **Submit stays home (5A):** `ImportForm` on the authenticated home no longer navigates; the 202 response's document prepends as an importing row. The anonymous demo paste flow is untouched.
- **Liveness (2A):** per-row polling — each row whose `status === 'importing'` polls the *existing* `/api/bff/documents/[id]` route on the `DocumentPoller` cadence and settles in place. No list re-fetch, no merge logic; a retried old doc simply starts polling again wherever it sits. Transient poll failures keep the last state and retry next tick (existing `readDocument` → null behavior). Docs created out-of-band (future MCP imports, M3.6 scans) appear on next visit — recorded in TODOS.md for M3.6 speccing to own.
- **Failure state (3A):** if the server-side list fetch fails (API down, or mid-rollout 404 before the API deploy), the import box still renders and the list area alone degrades to the existing `StatePanel` "API unreachable" idiom. The home never 500s over the list.
- **Retry (7A):** extract the retry affordance from `ImportFailed` (pending guard, transient-vs-dead-PAT branch, error copy) into a shared hook/subcomponent consumed by both the doc-page state and the list row — refactor first, then add the second consumer.

**Design.** DESIGN.md panel idiom: rows as a `divide-y` list inside the existing `rounded-2xl` panel anatomy; mono `MetaChip`s for version/lifecycle (reuse the review-header chips), status hues per the token table (emerald ready/open, amber in-review, rose failed), importing rows use the existing spinner treatment from `DocumentPoller`. No new tokens, no webfonts. **A11y (10A):** the status cell sits in an `aria-live="polite"` region announcing settle ("Import ready: {title}"); rows are real links; retry is a focusable button with the standard emerald focus ring.

**Testing (9A — the full traced matrix).**
- *PHPUnit (7):* rows newest-first with the lean payload shape; workspace scoping (IDOR matrix extension: user A never sees workspace B); `viewAny` 403 for a workspace-less reviewer; `per_page` clamp (`?per_page=100000` → 50, default 20); `open_threads_count` counts open threads only; response contains no document content; system-workspace demo docs excluded.
- *Vitest (3):* prepend-on-submit ordering; row-poll predicate (only `importing` polls; stops on settle); shared retry affordance branches (dead PAT → reconnect CTA, transient → retry).
- *E2E (2 + regression sweep):* new home-list journey — fresh user sees the empty state, imports from home, row prepends importing, a second import joins it, both settle ready, row click-through lands on the review surface; extend `import-failure.spec.ts` — failed import surfaces on the home row and inline retry recovers. **Regression (critical, 5A):** `importDocumentFromUrl` in `e2e/helpers.ts` changes its post-submit expectation from URL navigation to row-appears→click-through; every dependent journey in the pack is updated and re-greened in the same change.
- *Degraded home (3A):* unit-level static-markup assertion that a failed list fetch renders the import box + StatePanel (API-down e2e is not worth pack machinery).
- *Deliberately not e2e:* Load-more with 21 seeded docs — PHPUnit pagination + the vitest append test cover it; seeding 21 imports into the pack is pure runtime cost.

**Non-goals.** "Needs your attention" (M5 — needs notification data). Project chips/filtering (M3.6 — the row leaves a slot; `?project=` param arrives with it). A `?status=` filter param (no milestone owns it — SPEC §17 annotated accordingly). Search/sort (post-v1; newest-first only). Live appearance of docs created outside the page (M3.6's scan UX owns this — TODOS.md). Any schema change: this module is read-path only — `documents` already carries every field the row shows.
