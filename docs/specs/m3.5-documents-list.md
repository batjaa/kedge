# Spec: Documents list

> Module M3.5 on `docs/ROADMAP.md` (workspace UX wedge, decided 2026-07-21). Scope source: SPEC §11 ("Your docs" half, pulled forward from M5), §21 M3.5; API sketch §17 (`GET /documents`); testing §18. Language: CONTEXT.md. Decision context: TODOS.md decision log 2026-07-21. Specced 2026-07-21.

## Problem Statement

A workspace can hold any number of documents, but the authenticated home renders a greeting and an import box — nothing else. Every doc a user has ever imported is reachable only by remembering its URL or replaying browser history. Import is asynchronous, and each document's progress is visible only on its own page; kick off three imports and there is no screen that shows how any of them are doing. The M5 "review-queue dashboard" was going to fix this, but it is bundled with notifications for the sake of its *other* half ("Needs your attention") — the "Your docs" half has no notification dependency at all, and waiting two milestones to see your own documents is dogfooding pain today.

## Solution

The authenticated home becomes the workspace documents list. Under the existing import box, every document in the workspace, newest first, paginated: title, lifecycle chip, open-thread count, last-sync state and time, and — for docs still in flight — a live import status that settles in place (importing → ready/failed) without a refresh. Failed rows show the import error and retry inline through the existing retry endpoint (including the M1 nuance: a dead PAT offers "reconnect in Settings", not a futile retry). Rows click through to the review surface. M5 later stacks "Needs your attention" on top of this list; M3.6 adds project grouping to the same rows — the row anatomy is designed with a project chip slot from day one.

## User Stories

1. As an author, I want the home page to list every document in my workspace (newest first, paginated), so that nothing I import is ever lost to URL memory.
2. As an author, I want each row to show lifecycle status, open-thread count, and last-sync state/time, so that I can triage my docs at a glance.
3. As an author, I want documents that are still importing to show live progress on the list and settle to ready or failed in place, so that I never have to refresh to learn an import's fate.
4. As an author, I want to kick off several imports and watch all of them from this one screen, so that bulk-ish importing stops being blind.
5. As an author, I want a failed row to show why it failed and offer Retry inline — or "reconnect in Settings" when the cause is a dead PAT — so that recovery starts where I see the failure.
6. As an author, I want clicking a row to open the review surface, so that the list is the workspace's front door.
7. As an author with no documents yet, I want the list area to say so and point at the import box, so that the empty state teaches the entry point.
8. As a security reviewer, I want the list endpoint policy-scoped to workspace membership and paginated at the database, so that it discloses exactly what `GET /documents/{id}` would allow, page by page.
9. As a maintainer, I want the row payload to come from one aggregate query (open-thread count via a single eager-loaded count, current-version sync fields eager), so that the home page cost stays flat as a workspace grows.
10. As a maintainer, I want the list to poll only while at least one visible row is importing and stop when none are, so that an idle home page issues zero background requests.
11. As a maintainer, I want an e2e journey that imports from home and watches the row settle to ready, so that the list's liveness — its whole point — is regression-guarded.

## Implementation Decisions

**API.** New `GET /api/v1/documents` (`DocumentController@index`): workspace-scoped through the existing Policy, `latest()` order, page-based pagination (match the threads convention), `withCount` for open threads, eager `currentVersion` limited to the fields the row needs (`synced_at`, sync state lives on the document). Row resource is deliberately lean — no content, no approvals roster (that's the doc header's job). Demo-expired docs excluded by the same scope that hides them elsewhere.

**Web.** `ReviewQueue` on `app/page.tsx` grows the list under the import panel (inside the existing `PageContainer`). Server component fetches page 1 via the BFF; a client island owns subsequent polling and pagination ("Load more", appending). Polling generalizes the `DocumentPoller` pattern to the list: while any loaded row has `status === 'importing'`, re-fetch the loaded pages on the existing poller cadence; stop when none do. Import submission already navigates to the new doc's page — keep that; the list is where you land *back*.

**Design.** DESIGN.md panel idiom: rows as a `divide-y` list inside the existing `rounded-2xl` panel anatomy; mono `MetaChip`s for version/lifecycle (reuse the review-header chips), status hues per the token table (emerald ready/open, amber in-review, rose failed), importing rows use the existing spinner treatment from `DocumentPoller`. No new tokens, no webfonts.

**Testing.** PHPUnit: index scoping (member sees own workspace only — IDOR matrix extension), pagination, open-count correctness, demo-doc exclusion. Vitest: a pure `shouldKeepPolling(rows)` helper plus list-merge logic. E2E: extend the pack with the home-list journey (import → row shows importing → settles ready → click-through), reusing the fixture host.

**Non-goals.** "Needs your attention" (M5 — needs notification data). Project chips/filtering (M3.6 — the row leaves a slot). Search/sort controls (post-v1; newest-first only). Any schema change: this module is read-path only — `documents` already carries every field the row shows.
