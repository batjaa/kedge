# Spec: AI & agents

> Module M4 on `docs/ROADMAP.md`. Scope source: SPEC §21 M4; AI features SPEC §14; MCP server SPEC §15; security SPEC §13 (prompt injection, human-only actions); data model SPEC §16 (`ai_runs`); API sketch SPEC §17; testing SPEC §18 (§18.4 IDOR MCP-token column, §18.8 faked AI); observability SPEC §19. Language: CONTEXT.md. Specced 2026-07-20.

## Problem Statement

A review generates more words than the author can act on. Twenty threads across a spec — some contentious, some consensus, some drive-by nits — and the author's only tool is reading them all, holding them in their head, and hand-assembling the revision. A reviewer opening a forty-reply thread has no way to learn its current state short of reading forty replies. A sprawling comment that raises three separate issues stays one thread unless someone manually forks it three times. And the product's headline claim — **AI agents are first-class reviewers** — is currently false: the agent badge renders, the `client: mcp` column sits in the schema, and no agent has ever been able to connect, read a document, or post a comment. Kedge's own docs are reviewed in Kedge (dogfooding), but the coding agent that *writes* those docs is locked out of the review conversation it should be closing the loop on.

## Solution

Two halves of one loop. **AI drafting features** turn review noise into author action: a one-click **digest** (themes, contention points, consensus, action items — with honest coverage when the doc is too big to fit), an **improve-the-doc prompt** ready to paste into a coding agent — unresolved feedback by section, accepted suggestions verbatim as required edits, quoted anchors — per-thread **reply drafts** in the author's chosen stance, AI-proposed **comment splits** materialized through the existing fork flow, and **thread summaries** for the forty-reply monsters. Every output is a draft a human confirms — nothing auto-posts, ever. Runs execute async and land in a visible `ai_runs` ledger (status, model, tokens, cost) with a polling UI and a retry on failure. On an instance with no Anthropic key, the entire AI surface simply doesn't exist — no broken buttons.

**The MCP server** makes agents real reviewers: an operator mints a named, revocable agent token, points their agent at the Kedge MCP endpoint, and the agent lists documents, reads threads, and posts comments — through the same Policies as every human, badged violet as `AGENT · MCP`, visually a peer. Approvals and lifecycle stay human-only by construction: no MCP tool for them exists. The loop closes on Kedge's own docs: comments → digest → improve-prompt → Claude Code revises the source → re-sync → the comments survive.

## User Stories

1. As an author, I want a one-click review digest — themes, contention points, consensus, action items — so that I can absorb twenty threads without reading them serially.
2. As an author, I want the digest rendered in-app and copyable as markdown, so that I can use it outside Kedge (post-back to the source arrives in M6).
3. As an author, I want a digest over a doc too large for one model call to chunk by section and state its coverage ("digest covers N of M threads"), so that truncation is never silent.
4. As an author, I want an improve-the-doc prompt — doc context, unresolved feedback grouped by section, accepted suggestions included verbatim as required edits, quoted anchors — so that I can paste one artifact into a coding agent and get the revision the review asked for.
5. As an author, I want a per-thread reply draft honoring my chosen stance (accept / push back / clarify), landing in the composer as editable text, so that I can triage faster without the AI ever speaking as me unreviewed.
6. As an author, I want AI to propose splitting a sprawling comment into N threads (title + fragment + anchor each) that I approve individually before they become forked threads, so that multi-issue comments get tracked as separate conversations.
7. As a reviewer, I want a summary of a long thread — current state + the open question — so that I can join a forty-reply discussion without archaeology.
8. As any user, I want AI runs to be async with visible progress and a terminal status, so that a slow generation never blocks the page and a hung spinner never lies to me.
9. As any user, I want a failed run (Claude overloaded, rate-limited) to show as failed with a retry action, so that transient provider trouble costs one click, not a support thread.
10. As any user, I want every AI output clearly presented as a draft I confirm — nothing posts, accepts, or changes state on its own — so that the AI is a drafting tool, never an actor (hard rule 5).
11. As a self-hoster without an `ANTHROPIC_API_KEY`, I want the entire AI surface hidden — no buttons, no teasers, no errors — so that the product feels complete, not crippled, without a key.
12. As a workspace member, I want to mint a named agent token scoped to my workspace, see when it was last used, and revoke it, so that I control exactly which agents can act and can cut one off instantly.
13. As an agent operator, I want my agent to connect over MCP with its token and list documents, read a document (any version), list threads, and read a thread, so that it has the same review context a human reviewer has.
14. As an agent operator, I want my agent to post comments and replies — on an anchor or at document level — so that it participates in the review, not just observes it.
15. As a reviewer, I want agent comments visibly badged (violet ring, `AGENT · MCP` chip) and never disguised as human, so that I always know who — or what — I'm arguing with.
16. As an agent operator, I want to fetch the improve-prompt and digest over MCP, so that my coding agent can pull the review's marching orders directly instead of me copy-pasting.
17. As a security reviewer, I want no MCP tool for approvals, lifecycle changes, resolving threads, or accepting suggestions to exist at all, so that human-only actions are enforced by construction, not by policy checks that could regress.
18. As a security reviewer, I want every MCP tool to resolve through the same Policies as the REST API and the IDOR matrix to gain an MCP-token role, so that an agent token is never broader than its owner's access.
19. As a security reviewer, I want document and comment content fenced and labeled as untrusted data inside every AI prompt, so that a poisoned doc instructing the model is a named, mitigated threat — and MCP docs to warn agent operators that reviewed docs are an injection channel into *their* agents too.
20. As an operator, I want every run logged with type, model, tokens, and cost, and every MCP write audit-logged, so that AI spend per day and agent activity are observable from day one.
21. As an operator, I want AI endpoints and MCP tools rate-limited, so that a runaway agent loop can't burn the workspace's key or flood a review.
22. As an author, I want the full dogfood loop to work on Kedge's own docs — comments → digest → improve-prompt → Claude Code revises → re-sync → comments survive — so that the M4 demo criterion is a real workflow, not a staged one.

## Implementation Decisions

**Builds on M0–M3.** The agent-badge path is complete end-to-end and dormant: `comments.client` (web|mcp) with its backed enum, the client field on the comment resource, and the web's agent badge / violet agent-thread treatment (DESIGN.md) all ship — the first MCP-written comment lights them up with zero UI work. Comment split reuses the M2 fork-from-comment mechanism verbatim (idempotent, anchor-copying). Improve-prompt consumes M2's accepted suggestions (`proposed_text`, `suggestion_status`) and M3's version substrate. The async-status polling UI pattern (import status, new-version banner), the queued-job template (unique job, tries/backoff, terminal `failed()` writing status + audit), the append-only audit logger, the named-event `Log` idiom, the config capability endpoint that hides unconfigured features, the 404-when-disabled feature-flag middleware, the named throttle groups, and the IDOR matrix harness are all established patterns this module extends rather than invents.

**Packages and gating.** `laravel/ai` (Claude provider) and `laravel/mcp` join the api. Default model `claude-sonnet-5`; thread summaries on `claude-haiku-4-5` (high-volume cheap op); both env-overridable. **BYO key**: the AI surface is flag-gated on a configured `ANTHROPIC_API_KEY` — the capability endpoint exposes an `ai.enabled` boolean the web reads to hide every AI affordance; AI routes 404 when disabled (the established flag-middleware pattern). **MCP is gated independently** (`mcp.enabled`, default on): the server is an API surface, not an inference feature — an instance with no Anthropic key still hosts agent reviewers; only the two AI-artifact tools return an honest "no digest/prompt has been generated" result there.

**The `ai_runs` ledger.** New table per SPEC §16: `workspace_id`, `document_id`, `created_by`, backed-enum `type` (digest | improve_prompt | reply_draft | split | summary), backed-enum `status` (pending | running | completed | failed), `input` (assembled prompt metadata + scope refs, not raw secrets), `output` (structured JSON per type), `model`, `tokens`, `cost`, `error`. FK indexes throughout. Runs are **append-only cost/audit history**: retry mints a new run via a fresh POST; a failed run is never mutated back to life. `GET /ai-runs/{id}` is the single polling endpoint, guarded by an `AiRunPolicy`.

**Endpoints and jobs.** Per SPEC §17: `POST /documents/{id}/ai/digest`, `POST /documents/{id}/ai/improve-prompt`, `POST /threads/{id}/ai/reply-draft {stance}`, `POST /comments/{id}/ai/split`, and thread summary alongside them — each authorizes via Policy, creates a pending `ai_runs` row, dispatches one shared queued job (unique per run, mirroring the resync job's shape), and returns 202 + run id. **Duplicate generation is deduped server-side** (eng review 2026-07-20, §8): a POST while a pending/running run of the same (target, type) exists returns *that* run (200) instead of minting — double-clicks and returning users can't double-bill — and the web panel loads the latest run on mount so an in-flight or completed run is re-attached, never forgotten. The job assembles the prompt through a per-type builder service, calls Claude, writes `output`/`tokens`/`cost`, and lands `completed`. **Failures adopt the M1 deterministic/transient split** (eng review §5, the #55 bug class): provider overload / timeout / 5xx retries with backoff then lands `failed`; an invalid or removed key, a content-policy refusal, or post-SDK-retry unparseable structured output **fails immediately, no retries** — each with a specific `error` and the web showing "Generation failed — retry" (retry = a fresh POST, minting a new run). **Stuck runs are impossible from both sides** (eng review §6): an explicit job timeout fires the terminal handler (run → `failed`), and the web poller independently shows "taking too long — retry" past a client ceiling, covering even a hard-killed worker; the timeout is sized generously for chunked runs. A new `throttle:ai` limiter wraps all five. Digest **post-back** (`/ai/digest/post-back`) is M6 and does not ship.

**Context budget and honest coverage.** Prompt builders measure assembled input against a per-model context budget; over budget → chunk by section, merge per-chunk outputs, and record coverage in `output` ("covers N of M threads") which the UI renders verbatim. Never silent truncation (SPEC §14). Assembly eager-loads a document's threads and comments in one query — the context budget, not pagination, is the volume guard on this path.

**Shared prompt-assembly foundation** (eng review 2026-07-20, §10). Fence delimiters, untrusted-data labeling, budget math, chunking, and coverage accounting live in **one shared foundation** that all five builders compose; per-type builders only select content and shape output. Fencing is the SPEC §13 injection mitigation — it must be structural, not five-times-copied discipline a sixth builder could forget.

**Draft-only, by construction.** No AI feature writes review data. Digest and improve-prompt are displayed/copyable artifacts. Reply drafts populate the composer client-side — posting is the human's normal submit. Split proposals render as a review list; each approved split is materialized by the client calling the **existing fork endpoint** — the AI proposed, the human's approval is the write, through the same authorized path as a manual fork. To carry the proposal's per-fragment anchors, **the fork endpoint gains an optional client-supplied anchor** (eng review 2026-07-20, §9), validated against the current version's projection exactly like M3 re-attach (same trust boundary) before persisting; absent → today's copy-the-source-anchor behavior, unchanged. Zero side effects from any model output (hard rule 5).

**Prompt injection is a named threat** (SPEC §13). Document and comment content is delimited/fenced in every prompt and labeled as data, never as instructions. The draft-only invariant is the backstop: even a fully injected output can only produce a weird draft a human reads. MCP documentation states prominently that reviewed documents are untrusted input to the *consuming* agent.

**Testing uses `laravel/ai`'s native faking — no custom client interface** (eng review 2026-07-20, §3, revising the original custom-seam pin). The official SDK ships first-class fakes (`Agent::fake()` with scripted responses, `assertPrompted()` for asserting assembled prompts, auto-generated structured-output fakes) — rolling our own interface would rebuild a framework built-in and hide the SDK's assertion vocabulary from tests. Prompt builders stay plain services; tests script the SDK fake for success, provider-overload failure, and partial-coverage/chunked responses. **No live Claude call in any suite**; real-key verification is manual dogfooding on the dev instance (confirmed 2026-07-20).

**MCP server.** `laravel/mcp` in the api app, HTTP transport, exposing exactly SPEC §15's tool table: `list_documents`, `get_document(version?)`, `list_threads`, `get_thread` (read); `post_comment(thread?/anchor?)`, `reply(thread)` (write, stamped `client: mcp`); `get_improve_prompt`, `get_digest` (read of the **latest completed run** for the document — MCP never triggers generation, so an agent can't burn the key; generation stays a human act in-app). **AI artifacts carry staleness metadata** (eng review 2026-07-20, §4): generated-at, the version the run was built against, its coverage statement, and a computed stale flag when the current version or thread count has moved since — an agent must never act on Monday's marching orders without knowing Wednesday happened. Tools are thin adapters: zero business logic, delegating to the same services and resolving the same Policies as REST; list tools paginate like every list endpoint (SPEC §17). **No tool exists** for approve, lifecycle, resolve, accept/decline suggestion, or share — human-only actions are absent from the surface, not guarded on it. MCP writes are rate-limited and audit-logged; an anchor-bearing `post_comment` runs the same anchor validation as the REST capture path (same trust boundary).

**Agent tokens are MCP-only, by construction** (eng review 2026-07-20, §1 — the review's central decision). Sanctum personal access tokens arrive (token migration + `HasApiTokens`; SPEC §16 gains a "`personal_access_tokens` = standard Sanctum table" one-liner): named per agent, minted from a settings surface, shown once at creation (the Share-token idiom), listed with last-used, revocable instantly. Sanctum's default would let those bearer tokens authenticate on **every** existing `auth:sanctum` REST route — handing agents the human-only endpoints (approvals, lifecycle) and silently bypassing the closed MCP tool list. So a middleware on the REST `v1` group **rejects any request authenticated via a personal access token**: tokens are valid only on the MCP route group, the BFF cookie path is untouched, and "human-only by construction" survives as one structural rule. A pleasant corollary: since mint/revoke live on REST, **tokens cannot self-replicate** — an agent can never mint another token. **Workspace scoping is enforced in the shared Policy membership trait** (eng review §2), not per-tool: an actor authenticated via a token lacking the target resource's `workspace:{id}` ability is denied by the same trait every current and future Policy already inherits — no tool author can forget the check. **Token mint/list/revoke sit behind a Policy requiring full workspace membership** (eng review §7): M2's reviewer shadow-users are real authenticated `User` rows, and a reviewer minting a token would escalate one shared document into an MCP credential — the Policy denies them structurally, and the IDOR matrix proves it. Comments an agent posts attribute to the token owner's identity plus the agent badge — the human who minted the token owns what their agent says.

**Web surface.** An `ai-client` following the established client idiom (POST → run id → poll to terminal status, reusing the poller pattern, plus the load-latest-run-on-mount re-attach and the taking-too-long ceiling state). Per DESIGN.md: the primary **AI-digest button** in the document header opening a digest panel (in-app render + copy-as-markdown + coverage line); improve-prompt generation and copy from the same surface; **"Draft reply →"** with a stance picker in the thread panel footer — inserting directly into an empty composer, but **never silently replacing typed text**: a non-empty composer gets an explicit "Replace your draft?" confirmation (eng review 2026-07-20, §12 — the human-confirms invariant applied to the human's own words); split proposal review (approve per-split / all); thread summary affordance on long threads; and the agent-token management settings page. All of it absent when `ai.enabled` is false (tokens/MCP settings remain, gated on `mcp.enabled`), and **a config payload missing the `ai` capability is treated as false** — the same fail-closed rule as M1's `self_hosted`, so a new web against an old api shows nothing broken.

**Observability.** Named events per the established `Log` + audit idiom: `ai_run.started/completed/failed{type, model, tokens, cost}` (powers the AI-cost/day metric, SPEC §19), with `failed` carrying the error kind (deterministic vs transient — the alertable split) and `completed` carrying `chunked` + coverage so budget pressure is observable; `mcp.tool_invoked{tool}` on writes; token mint/revoke audit-logged. The §19 failure registry gains the AI rows it already names (overloaded → failed + retry; context overflow → chunked coverage).

**Language.** CONTEXT.md gains **Agent** (a non-human reviewer acting over MCP under a member's token), **Agent Token** (the named, revocable, workspace-scoped credential), and **AI Run** (one queued generation with its cost ledger) in the schema-landing commit.

## Testing Decisions

The three established seams, extended (confirmed 2026-07-20). Good tests assert external behavior — what a run returns over HTTP, what an MCP tool call persists, what renders — never prompt wording or matcher internals.

1. **API HTTP seam (PHPUnit) — primary.** AI-run lifecycle end to end against the faked AI client: each endpoint → 202 + pending row → job → completed output shape; provider-overload → `failed` + error surfaced; chunked/partial-coverage output carries its coverage statement; retry mints a new run, never mutates the failed one; the improve-prompt's captured fake input contains accepted suggestions verbatim and fenced untrusted content (asserted via the fake's recorded request, not prompt-string goldens); `ai.enabled` off → 404 and capability boolean false. MCP tools exercised in-process through `laravel/mcp`'s test utilities: each tool × Policy outcomes, writes persist `client: mcp` and are audit-logged, anchor validation on `post_comment`, workspace-scoped token abilities enforced, revoked token → 401, and **the tool list itself asserted closed** (no approve/lifecycle/resolve tool exists). The IDOR matrix gains the `ai-run` action column across existing roles and the **MCP-token role row** across existing actions (SPEC §18.4).
2. **Web seam (Vitest) — small.** Pure helpers only: run-poller state transitions (pending → completed/failed, retry), split-proposal shaping, digest copy-as-markdown serialization, coverage-line rendering. Golden fixtures where the existing pattern fits.
3. **E2E journey pack (Playwright).** The M4 journeys, per the journey-per-surface philosophy (eng review 2026-07-20, §11): **(a)** the demo criterion — a **real MCP client hop**: a Node MCP SDK script connects to the served api's MCP endpoint with a token minted through the settings UI, posts a review comment; the browser asserts the violet agent badge; the author generates a digest and improve-prompt (faked AI via the e2e environment, sync queue completes runs inline) and copies the prompt; token revocation → agent's next call fails. **(b)** an `ai-triage` journey: reply draft with a stance → edit → post; thread summary renders. **(c)** an `ai-split` journey: propose → approve two splits → two forked threads exist with their own anchors. Unique users/docs per spec, zero retries, prior journeys untouched.

**Review-mandated test gaps** (eng review 2026-07-20, carried into ticket acceptance criteria): **G1** every REST v1 action × MCP-token principal → rejected (the tokens-are-MCP-only rule, extending the IDOR matrix wholesale); **G2** a token lacking the target's workspace ability is denied through the Policy trait (cross-workspace agent read/write attempts); **G3** MCP artifact staleness metadata — fresh run → not stale, post-re-sync/new-thread → stale flag set; **G4** deterministic failures (bad key, unparseable structured output) fail immediately with no retries while transient failures retry then fail — asserted via the SDK fake; **G5** job timeout lands the run in `failed`, and the poller helper reaches the taking-too-long state (Vitest); **G6** reviewer-via-share and demo principals cannot mint/list/revoke tokens (IDOR rows); **G7** a duplicate POST while a run is pending/running returns the existing run, and the panel re-attaches to the latest run on mount; **G8** fork with a valid client anchor persists it, an invalid anchor is rejected, and — **CRITICAL regression test** — fork *without* an anchor keeps M2's copy-the-source-anchor behavior byte-for-byte; **G9** fencing/labeling is asserted once at the shared foundation plus a composition check per builder (`assertPrompted`); **G10** a zero-thread digest completes with an honest empty output, never an error; **G11** MCP list tools paginate; **G12** the reply-draft composer confirmation — empty composer inserts, non-empty composer never replaces without confirm (Vitest component).

**No live Claude anywhere in CI.** The SDK fake covers success, failure, and partial coverage (SPEC §18.8); a real-key digest on Kedge's own SPEC.md is the manual dogfood check before the module closes.

## Out of Scope

- **Digest post-back** to PR/Confluence (`Connector::postComment`) — M6. The digest ships copy-as-markdown only.
- **Notifications** for agent comments, AI-run completion emails, mentions-by-agents fan-out — M5. Persistence never depends on fan-out (hard rule 6); in M4 there is no fan-out.
- **Review-queue integration** (agent activity in the dashboard) — M5.
- **MCP-triggered generation** — agents fetch AI artifacts, never mint runs; generation is a human act in-app (deliberate: key protection + draft-only clarity).
- **MCP tools for approvals, lifecycle, resolve, suggestions, shares** — deliberately absent forever, not deferred (SPEC §15).
- **Streaming AI output / realtime run updates** — polling in v1; Reverb later (accepted debt).
- **Fine-grained agent permissions** (per-document tokens, read-only tokens) — workspace-scoped abilities only in v1; sharpen on real agent usage.
- **Non-Claude providers / BYO-model abstraction** — `laravel/ai` → Claude is the v1 pin (SPEC §14).

## Further Notes

- **Demo criterion** (SPEC §21 M4): *an agent connects over MCP and posts a review comment; author closes the loop: comments → digest → improve-prompt → Claude Code revises → re-sync.* The e2e journey automates the first half; the full loop is the manual dogfood on Kedge's own docs — this module's spec review comments should themselves be digested by the feature they specced.
- **AI cost/day is a day-1 metric** (SPEC §19) — `ai_run.completed{model, tokens, cost}` powers it; the append-only ledger means cost history survives retries.
- The MCP surface is the moat's second half (comments surviving versions is the first): agent-as-reviewer is the differentiator named in SPEC §1 — treat the closed tool list and the badge honesty as product identity, not implementation detail.
- **Sequencing suggestion for tickets**: the `ai_runs` ledger + SDK-fake wiring first (everything else lands on it), then the five features (digest and improve-prompt carry the demo), then Sanctum tokens + MCP server, then the e2e journeys last.
- **Deployment carry-overs** (not code in this module): the preview/SaaS env needs `ANTHROPIC_API_KEY` provisioned for dogfooding (same class as M3's `MAIL_*` carry-over). Post-deploy verification: one real digest on a real doc + one MCP smoke call with a freshly minted token.
